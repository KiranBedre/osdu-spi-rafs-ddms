# Thermal Compositional Fluid Model v1.0.0 — new content schema

Adds `thermalcompositionalfluidmodel` as a third FluidModel content schema type, alongside
`blackoilfluidmodel` and `compositionalfluidmodel`:

```
POST /api/rafs-ddms/v2/fluidmodel/{record_id}/data/thermalcompositionalfluidmodel
GET  /api/rafs-ddms/v2/fluidmodel/{record_id}/data/thermalcompositionalfluidmodel/{content_id}
```

Both routes are the existing generic FluidModel data routes; only the content schema and
its generated model (`ThermalCompositionalFluidModelModel100`) are new.

## Source

Generated with the OSDU schema composer from
`ThermalFluidModel.1.0.0_InterimDevUseNotFinal.xlsx`.

**The source workbook is marked *InterimDevUseNotFinal*.** Enthalpy, the K-value
correlations and the three viscosity-model variant sets are still being authored
upstream, so field names, descriptions and the `oneOf` variant lists are expected to
change before the schema is final. Nothing in the endpoint behaviour depends on those
fields.

## Naming

The URL segment, the schema file and the generated model all use
`thermalcompositional` / `ThermalCompositional`, matching the OSDU reference value
`reference-data--FluidModelType:ThermalCompositional` (see
`ReferenceValues/Manifests/reference-data/OPEN/FluidModelType.1.json`, whose three
entries are `BlackOil`, `Compositional`, `ThermalCompositional`). That value is what
`FLUID_MODEL_TYPE_MAPPING` supplies to the search query in
`app/search/fluid_model_ids_fetcher.py`, so it has to match the reference data exactly or
`/thermalcompositionalfluidmodel/search` silently returns an empty result set.

This deliberately diverges from the OSDU content-schema entity, which the workbook still
calls `ThermalFluidModel`. Keep the `ThermalCompositional` naming when the schema is
regenerated from a later workbook revision.

## Deferred out of v1.0.0

The workbook marks three root fields `No Change` / `Deferred`; they are deliberately
absent from this version:

- `VaporPhaseDensities`
- `LiquidPhaseDensities`
- `WaterThermalModel`

## Deviation from composer output

`Enthalpy.description` was replaced with "The enthalpy model used for the fluid phases."
The workbook's description cell holds an internal authoring note that would otherwise
ship into the public OpenAPI documentation.

## Endpoint coverage

Both routes are the shared generic FluidModel data routes, so no route code was added.
The behaviour named in the acceptance criteria is asserted per type in
`tests/test_api/test_routes/data/data_v2_test.py`:

| Case | Result |
|------|--------|
| `record_id` not matching the FluidModel pattern | 422 |
| `content_id` matching neither the dataset nor the UUID pattern | 422 |
| Malformed `content_schema_version` (`abc`, `1`, `1.0.0.0`, …) | 422 |
| Well-formed but unimplemented version (`9.0.0`) | 404 |
| No version in either the query parameter or the `Accept` header | 406 |
| `content_schema_version` alongside a different `Accept` version | query parameter wins |
| `Accept` absent or `*/*` | JSON |
| `Accept: application/x-parquet` | parquet |
| Unsupported `Accept` (e.g. `application/xml`) | 406 |
| Invalid `columns_filter` / `rows_filter` / `columns_aggregation` | 422 |
| `content_id` not listed in the record's `DDMSDatasets` | 404 |
| Version in the dataset URN disagreeing with the record's `DDMSDatasets` entry | 400 |

A separate "content missing → 422" state is not reachable through the public API: 422 on
this route comes only from `content_id` pattern validation, so it is not covered here —
same as for the two sibling types.

Caching is asserted only as far as the unit suite allows. `tests/conftest.py` replaces
`fastapi_cache.decorator.cache` with a pass-through for the whole unit suite, so the
served-from-cache behaviour cannot be exercised in process; the unit test asserts instead
that `key_builder_using_token` is deterministic per request and discriminates on token,
partition and query parameters. Identical-response-inside-TTL is covered end to end by
the integration suite against the same shared handler
(`test_black_oil_get_data_returns_identical_response_inside_cache_ttl`).
